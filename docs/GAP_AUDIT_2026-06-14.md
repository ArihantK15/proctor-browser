## Cluster 1 — CSP blocks inline scripts on standalone server-rendered pages

Global CSP is `script-src 'self'` with no `'unsafe-inline'`/nonce (`app/main.py:582`).
Dashboard + static HTML were migrated to `data-action` delegated listeners; these
standalone Python-rendered pages were not, so their inline `<script>` is silently
blocked in production.

| Page | File | Impact | Sev |
|---|---|---|---|
| Reset password | `app/routers/auth.py` (RESET_PASSWORD_HTML) | form JS blocked (user already fixing) | 🔴 |
| Org-invite acceptance | `app/routers/auth.py:1135` | ✅ FIXED — externalized to `/static/invite-accept.js`, token via `data-token` | ~~🔴~~ |
| LTI deep-link return | `app/lti/deeplink.py:238` | see Cluster 2 | 🔴 |
| Admin system-status page | `app/routers/admin_status.py:50` | `/status-page` never renders | 🟠 |
| Google Classroom OAuth close | `app/routers/google_classroom.py:84` | popup won't auto-close | 🟡 |

Fix: externalize JS to a `'self'`-served file or use a CSP nonce.

## Cluster 2 — LTI deep-linking doubly CSP-broken (shipped, advertised feature)

LTI is advertised (pricing, Trust, `/lti-setup`, comparison pages). Deep-link return
(`app/lti/deeplink.py:235`) renders `<form method=post action="{external LMS url}">`
auto-submitted by an inline script. Two directives block it:
1. `script-src 'self'` → auto-submit script never runs.
2. `form-action 'self'` → manual submit can't POST to the external LMS either.

Deep linking cannot work under the current CSP. Needs per-route CSP (allow LMS origin
in `form-action`) + externalized/nonced script.

## Subsystem A — Exam submit / scoring / autosave

### A1 🔴 Mis-scoring for multi-exam teachers with shuffle ON
`recalculate_score` (`app/services/scoring.py:147`) re-canonicalises the final-submit
`payload_answers` by calling `canonicalise_student_answer(...)` **without** `exam_id`,
even though it received `exam_id` and uses it correctly for `load_questions` two lines
above (line 141). `canonicalise_student_answer(exam_id=None)` →
`load_questions(teacher_id, None)`, and `load_questions` **skips the exam filter when
exam_id is falsy** (`app/repositories/questions.py:27`, `if exam_id:`), returning
**ALL of the teacher's questions across every exam**. `build_shuffle_view` then shuffles
that wrong superset, so the de-shuffle (`translate_student_answer`) maps the submitted
answers with the wrong per-question option permutation → **silently wrong score**.
- Bites: any teacher with ≥2 exams and shuffle enabled (shuffle defaults ON).
- Worse: `payload_answers` overwrites the correctly-canonicalised autosaved answers
  (scoring.py:145 reads DB answers raw — those were saved correctly via `save_answer`
  which DOES pass `eid`, `app/routers/exam.py:984`). So even correctly-saved answers
  get corrupted at score time.
- Single-exam teachers unaffected (None still resolves to their only exam's questions).
- Fix shape: pass `exam_id=exam_id` into the `canonicalise_student_answer` call at
  scoring.py:147 (one-arg fix). Likely masked by single-exam test fixtures.

### Verified solid (submit path)
- Double-submit: API-edge guard rejects COMPLETED/FORCE_SUBMITTED/REJECTED and short-
  circuits SUBMITTED (`exam.py:1246`); ABANDONED is recoverable by design.
- Numeric-range grading (`range:MIN:MAX`), multi-answer set equality, true/false
  no-shuffle handling all correct (`scoring.py:62-95`).
- `save_answer` canonicalises with `eid` before persisting; shuffle seed is per-session
  (unique), so the seed itself needs no exam_id.

### A2 🟡 Double-submit guard is TOCTOU, but worker guard covers it
The `existing`-status SELECT (`exam.py:1246`) and interim UPDATE (`exam.py:1320`) aren't
atomic, so two genuinely-concurrent submits can both enqueue a scoring job. **Mitigated**:
`_score_submission_async` (`app/jobs/scoring_jobs.py:28`) re-checks status and bails on
COMPLETED/FORCE_SUBMITTED, so a single scoring worker is effectively idempotent. Residual
risk only if MULTIPLE scoring workers run concurrently and interleave between the guard
read and the COMPLETED write (double LMS passback). Low priority; note for when scaling
the scoring queue to >1 worker.

> A1 note: the async worker path is affected too. `_score_submission_async`
> (`scoring_jobs.py:69`) calls `recalculate_score(..., exam_id=exam_id)`, which still
> hits the exam_id-less canonicalise at scoring.py:147 — so the mis-scoring is in BOTH
> the inline and worker scoring paths.

### A3 🟠 Async-submit flush/scoring queue race (potential stale score)
In the queued submit path, the final bulk snapshot is cached and a flush job is enqueued
on the **`autosave`** queue with `delete_after=True` (`exam.py:1015-1021,1299`), while the
scoring job is enqueued on the **`scoring`** queue (`exam.py:1336`). Different queues = no
ordering guarantee. `_score_submission_async` loads answers from **DB** (`scoring_jobs.py:64`),
ignoring the cache. If scoring runs before the flush lands (or the flush fails after the
cache delete), the score reflects pre-final-snapshot answers.
- Mitigation in practice: per-question `save_answer` writes straight to DB
  (`exam.py:996`), so the DB is usually current; the race only loses answers that existed
  *only* in the final bulk cache snapshot, not yet individually saved.
- Fix shapes: chain scoring as a dependent of the flush job, or have the scoring job
  flush-then-read (read cache first, fall back to DB), or run final flush synchronously
  before enqueueing scoring.

## Subsystem B — Proctoring (events, frames, risk score)

### Verified solid
- IDOR-safe ingestion: `/event` + `/heartbeat` call `_assert_student_session_access`
  (`exam.py:790-792,898-900`); `/live-frame` checks the JWT `roll` claim against the
  session key prefix AND the DB row (`sse.py:180-199`). A student cannot poison another
  student's risk score.
- Risk algorithm (`app/services/risk.py`): log-saturating per-type contribution,
  severity multipliers, duration-normalized, 3h span cap (handles reaper/resume spans),
  dismissed-flag exclusion (`is_("dismissed_at","null")`). No correctness gap found.

### B1 🟡 Risk undercount if a violation row lacks teacher_id
`compute_risk_score(teacher_id=X)` adds `.eq("teacher_id", X)` to the violations query
(`risk.py`). Any violation row persisted with a NULL `teacher_id` is then silently
excluded from the score → undercounted risk (missed cheating). Worth confirming every
violation-writer always stamps `teacher_id`. Low confidence; flagged to verify.

## Subsystem D — Electron secure browser (kiosk integrity)

### D1 🔴🔴 Kiosk lockdown is bypassable by a command-line flag, in production
`KIOSK_ALLOWED = !process.argv.includes('--no-kiosk') && process.env.PROCTOR_DEBUG !== '1'`
(`config.js:7`) has **no `app.isPackaged` / production guard**. So in a shipped build a
student can launch `Procta.exe --no-kiosk` (or set `PROCTOR_DEBUG=1`) and get
`isKiosk=false`, which (`lib/kiosk-manager.js:320-361`):
- creates the exam window with `kiosk:false, fullscreen:false, alwaysOnTop:false, frame:true`,
- sets `devTools:true` and **auto-opens DevTools** (`openDevTools()` when `!isKiosk`),
- skips the blocked-shortcut registration.

There is **no refuse/abort/warn** when kiosk is off — the exam loads and runs unlocked.
With DevTools open in the renderer the student can read questions, edit answers, disable
the on-device camera/AI pipeline, and suppress violation POSTs. This defeats the core
"secure browser" guarantee.

Compounding: the client **does not report kiosk/lockdown status to the server**, and the
exam-start/validate endpoints don't verify it (grep for kiosk attestation in
`exam.py`/`public.py` → none). So the server can't even tell a session ran unlocked.

Fix shape: gate `--no-kiosk`/`PROCTOR_DEBUG` behind `!app.isPackaged`; refuse to start a
real exam when `KIOSK_ALLOWED` is false; and send a signed kiosk attestation the server
verifies (and flags/blocks sessions without it).

Honest caveat: read from source, not a run of the packaged binary — but the flag's
definition is unconditional, so unless overridden elsewhere it is honored in prod.

### Verified solid (Electron)
- Secure webPreferences everywhere: `contextIsolation:true, nodeIntegration:false,
  sandbox:true` (kiosk-manager.js:129,335).
- `will-navigate` blocked + `setWindowOpenHandler(() => deny)` (no nav-away / popups).
- Broad blocked-shortcut set incl. macOS-specific escapes (Spotlight, screen-record,
  Mission Control, Spaces) — `config.js:14-37`.
